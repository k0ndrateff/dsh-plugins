# План развития: от одного плагина к рабочему тулкиту

Документ отвечает на три вопроса: как разложить плагины архитектурно, как
докрутить четыре задуманные интеграции, и что имеет смысл сделать сверх них.
Он написан по фактам, снятым с живых эндпоинтов и из исходников DSH `0.2.1-rc.2`;
там, где факта нет, это сказано прямо.

Обозначения: **проверено** — снято с живого сервера или из кода харнесса;
**предположение** — гипотеза, требующая прототипа.

---

## 1. Точка отсчёта: что уже есть

| Слой | Состояние |
|---|---|
| OAuth для MCP | Полный цикл: RFC 9728 (PRM), RFC 8414 (AS metadata), RFC 7591 (DCR), PKCE S256, loopback-редирект с подбором порта, refresh под кросс-процессным локом, запись в credential-сторе |
| Мост к MCP | Свой транспорт с `authProvider`, публикация обнаруженных тулов через штатный адаптер харнесса |
| UI | Карточки в хвосте ответа (`presentationMeta` → turn tail), панель в правом Sidebar (свой тип вкладки), терсные строки тулколов, секция в настройках |
| Сборка | esbuild для обеих половин, vanilla-extract с инлайном CSS в клиентский бандл, обёртка клиентского модуля |
| Тесты | 100 проверок: чистые функции, парсеры MCP-фикстур, маршруты, плюс живой dry-run OAuth против обоих эндпоинтов Atlassian |

Главный вывод из этого: **дорогая часть — не интеграция, а OAuth и мост.** Каждый
новый провайдер — это «OAuth-профиль + список тулов + UI», и только первое
написано нами.

## 2. Архитектурный вопрос: один плагин или несколько

### Как харнесс раскладывает плагины (проверено)

- **Bundle** — npm-пакет с `dsh.bundle.patch`: это *слой конфигурации*, который
  вставляет строки плагинов. **Profile** — директория с `dsh.profile.bundles`,
  то есть список бандлов в порядке применения.
- Установка — `dsh plugin add`, который просто делегирует в pnpm в директории
  профиля. Значит единица распространения — **npm-пакет**.
- **Market** — JSON-индекс формата 1, который пользователь добавляет как
  источник. Каждый `MarketPlugin` — это один npm-пакет со списком версий
  (`source: npm | git`, `engines.dsh`), и в UI он ставится, обновляется и
  удаляется **по отдельности**.
- Пакет **без** `dsh.bundle` харнесс документирует отдельно: «installs as a
  plain dependency… use that package format for a library that plugin packages
  import rather than a plugin users enable».

### Рекомендация

**Монорепа, несколько мелких бандлов и три библиотеки.**

```
packages/
├── mcp-oauth/          библиотека: OAuth для MCP (без dsh.bundle)
├── integration-host/   библиотека: общий хостовый каркас интеграции (без dsh.bundle)
├── integration-ui/     библиотека: общая обвязка карточек и панели (без dsh.bundle)
├── plugin-build/       библиотека: build.mjs + styles-runtime (devDependency)
├── devkit/             бандл: проверки (lint/typecheck/tests/build)
├── atlassian/          бандл: Jira + Confluence
├── sentry/             бандл
├── gitlab/             бандл
├── figma/              бандл
└── workflow/           бандл-«мета»: patch, подключающий остальные
```

### Конвенции репозитория (по принятым решениям)

| Директория | Имя пакета | Тип |
|---|---|---|
| `packages/mcp-oauth` | `dsh-mcp-oauth` | библиотека |
| `packages/integration-host` | `dsh-integration-host` | библиотека |
| `packages/integration-ui` | `dsh-integration-ui` | библиотека |
| `packages/plugin-build` | `dsh-plugin-build` | библиотека (dev) |
| `packages/devkit` | `dsh-devkit-plugin` | бандл |
| `packages/atlassian` | `dsh-atlassian-plugin` | бандл |
| `packages/sentry` | `dsh-sentry-plugin` | бандл |
| `packages/gitlab` | `dsh-gitlab-plugin` | бандл |
| `packages/figma` | `dsh-figma-plugin` | бандл |
| `packages/workflow` | `dsh-workflow-plugin` | бандл-мета |

Все имена свободны в npm (проверено). Каждый бандл несёт:

- `dsh.bundle.patch` — слой конфигурации;
- `dsh.client` — браузерная половина, если она есть;
- `engines.dsh` — диапазон версий харнесса;
- `dsh.profile` не несёт никто: профиль собирает пользователь.

Для market-индекса (формат 1) каждый `MarketPlugin` требует ещё `title`,
`description`, `icon`, `author`, `repository` и версии с `source` (`npm` или
`git` + commit) и `engines.dsh` — то есть метаданные пишутся сразу, а не перед
релизом.

Почему не один большой плагин:

1. **Версия одна на всех.** Правка в мелочи Figma выпускает релиз всего, включая
   Jira-панель, и заставляет обновляться всех.
2. **Зависимости не разделяются.** GitLab тянет свои peers, Figma — свой
   attachments, devkit — jobs. В одном пакете их набор становится объединением,
   а `engines.dsh` — пересечением.
3. **Выключить нельзя по частям.** Пользователю, которому нужен только GitLab,
   придётся держать включёнными ещё четыре интеграции (и их настройки).
4. **Ревью и тесты мельче.** Пакет на 500 строк ревьюится, пакет на 5000 —
   просматривается.

Почему не четыре независимых репозитория: общий код придётся либо копировать,
либо версионировать через npm-публикации на каждую правку. Монорепа с
workspace-зависимостями даёт и то и другое, а «one repo per plugin» можно
получить позже, если какой-то плагин уедет в свою жизнь.

Компромисс для «хочу всё сразу» — бандл `all`: один patch, подключающий
остальные пакеты. Он ничего не содержит сам и никого не связывает версиями.

## 3. Фундамент: библиотека `dsh-mcp-oauth`

**Проверено:** в харнессе нет ни одной реализации OAuth для MCP. Стоковый
`dsh-mcp-client` берёт статический `Authorization` из конфигурации, и поиск по
всему дереву пакетов не находит ни PRM, ни DCR, ни PKCE. То есть это не
«переизобретение»: этого просто нет, и любой OAuth-провайдер в экосистеме
сегодня подключить нечем.

### Что уже проверено на живых серверах

| Провайдер | Ресурс | AS | DCR | PKCE | Что выдаёт DCR |
|---|---|---|---|---|---|
| Atlassian | `mcp.atlassian.com/v1\|v2/mcp` | `mcp.atlassian.com` | да | S256 | public (`none`); v2 кладёт в ответ ещё и секрет |
| Sentry | `mcp.sentry.dev/mcp` | `mcp.sentry.dev` | да | S256 | public (`none`) |
| GitLab | `gitlab.com/api/v4/mcp` | `gitlab.com` | да | S256 | **public (`none`)** — запрошенный метод игнорируется |
| Figma | `mcp.figma.com/mcp` | `api.figma.com` | **нет** | S256 | анонимный `POST` на register — 403 |

Детали, снятые запросами:

- **Atlassian v1 и Sentry**: `none` даёт публичного клиента без секрета, а
  `client_secret_post`/`client_secret_basic` — секрет. Оба метода прогнаны
  против живого token endpoint: с верным секретом ответ `invalid_grant`, с
  неверным — `invalid_client`. Значит confidential-путь библиотеки проверен, но
  не там, где его искали: GitLab и Figma секретов не выдают вовсе.
- **Atlassian v2**: `token_endpoint_auth_methods_supported` включает `none`, и
  DCR действительно возвращает `"token_endpoint_auth_method":"none"` — но вместе
  с `client_secret`. Token endpoint этой генерации сначала проверяет grant и
  только потом клиента: на любую заведомо негодную попытку (в том числе без
  клиента) он отвечает `invalid_request`, так что различить клиентов им нельзя.
- **GitLab**: метаданные объявляют только `client_secret_basic|post`, а
  `registration_endpoint` возвращает `"token_endpoint_auth_method":"none"`,
  `require_pkce: true` и никакого секрета — неверифицированное динамическое
  приложение. Токен-эндпоинт такого клиента принимает (с выдуманным кодом —
  `invalid_grant`, с неверным секретом — `invalid_client`). То есть **сессия
  GitLab поднимается из DCR как публичный клиент с PKCE**, без секрета.
- **Figma**: `registration_endpoint` объявлен и на `GET` отвечает 404, а на
  `POST` — 403 с `vary: X-Figma-Token, Authorization`: регистрация требует
  аутентификации, анонимного DCR нет. Клиента для Figma придётся заводить
  руками (см. решение 3).
- **Device flow**: у GitLab `device_code` есть в `grant_types_supported`, но
  `device_authorization_endpoint` не объявлен, `POST /oauth/device_authorization`
  — 404, а единственный известный `/oauth/authorize_device` отвечает
  `access_denied` на клиента из DCR. Библиотека без вендорского знания этот
  эндпоинт не найдёт, поэтому device flow в M1 не делался (см. M1 ниже).

### Что библиотека должна уметь (сверх сегодняшнего кода)

1. **Confidential client — это проверить, а не написать.** `client_secret` из DCR
   уже сохраняется в записи и отправляется в token request полем
   `client_secret_post` (`oauth/server.ts`, `toTokenFields`), а
   `client_secret_basic|post` — ровно то, что объявляют GitLab и Figma. Значит
   здесь работа — conformance-тест против них, а не новый код. Но именно поэтому
   его стоит сделать рано: если окажется, что GitLab требует basic-авторизацию
   или иной формат запроса, дешевле узнать это на M1, чем на M5.
2. **Мультиаккаунт и мультиинстанс.** Сейчас запись одна (`dsh-atlassian/mcp`).
   Нужен ключ `provider + instance` — иначе нельзя одновременно work-GitLab и
   личный, или gitlab.com и self-hosted. **Это надо сделать до второго
   провайдера**, иначе миграция записей задним числом.
3. **Manual client** — режим, когда DCR недоступен (self-hosted GitLab без
   регистрации) и client_id/secret вводит пользователь.
4. **No-auth** — локальный MCP без токена (Figma Dev Mode).
5. **Device flow** — опционально, для GitLab; даёт вход без браузера.
6. **Conformance-набор**: один dry-run, прогоняющий discovery/DCR/authorize
   URL/loopback/forged-state против всех четырёх провайдеров. Он станет главным
   аргументом «библиотека проверена на живом».
7. **Upstream.** Отдельным PR — хук `authProvider` в стоковый `dsh-mcp-client`
   или соседний плагин-провайдер. Это польза не только нам: без этого ни один
   OAuth-MCP в экосистеме не подключается.

**Состояние после M1.** Пункты 1, 2, 4 и 6 сделаны. Пункт 1 оказался не тем,
чем выглядел: публичного DCR у GitLab и Figma нет, зато секрет выдают Atlassian
и Sentry — там confidential-путь и проверен, обеими формами. Пункт 3 вернулся в
план: без анонимного DCR у Figma клиента придётся вводить руками (M6). Пункт 5
отложен по факту из раздела выше.

Оценка: **M** на обобщение + **S–M** на conformance и upstream. Риск низкий:
код работает, задача — вынести.

### Идея 1. Тулы для линтера, тайпчека, тестов и сборки

**Оценка: M. Самый независимый пункт — можно делать параллельно всему.**

Проблема сегодня: агент каждый раз набирает `bash`, и результат — это простыня
вывода, в которой тонут и ошибки, и прогресс. Нужны именованные проверки и
карточка с итогом.

**Дизайн: рецепты принадлежат проекту, а не агенту.** Это главное решение.
Конфиг в репозитории — `dsh-checks.json` в корне проекта:

```json
{
  "checks": {
    "typecheck": { "run": "bun run typecheck", "parse": "tsc" },
    "test":      { "run": "bun test",         "parse": "vitest" },
    "lint":      { "run": "bunx biome check", "parse": "biome" }
  }
}
```

Тул `checks` принимает **имя рецепта** (или `all`) и никогда — произвольную
команду: иначе это `bash` с лишним шагом. Агент выбирает, проект владеет
командой, а обычный permission-пайплайн продолжает работать.

Парсеры: `tsc`, `biome`/`eslint`, `vitest`/`jest`, `pytest`, `generic` (код
возврата + хвост вывода). `cargo` и `go test` отложены: их формат здесь не на чем
проверить. Результат структурный:

```ts
{ ok: boolean,
  checks: [{ name, status, durationMs,
             summary: { errors, warnings, testsPassed, testsFailed, testsSkipped },
             failures: [{ file, line, message }] }] }
```

**UI — тем же механизмом, что уже работает в карточках:**

- Строка тулкола: `checks · test ✓ 48/48 · typecheck ✗ 3 ошибки` — через
  `tool.call.toolview` (keyed по имени тула).
- Карточка в хвосте ответа через `presentationMeta` — с итогами по каждой
  проверке и списком файлов.
- **Клик по файлу открывает его в панели харнесса.** Проверено: owner-пропсы
  сиденья `conversation.chat.turnTail` — это `{ turn, seq, openFile }`, то есть
  `openFile(path)` доступен прямо в карточке. Это превращает «3 ошибки» в
  «показать мне их». Файл открывается с начала: строка в `openFile` есть только у
  сиденья `tool.call.toolview`, а карточка живёт в хвосте ответа.

Докрутки:

- **Watch-режим** (`checks watch typecheck`): держит процесс и отдаёт только
  дельты. Полезно в длинном цикле правок; риск — шум в контексте. **Не сделано.**
- **Длинные прогоны через jobs** (в харнессе есть `dsh-jobs`): `checks run test`
  в фоне, результат забирается `job_output`. **Не сделано**; пока рецепт держит
  тулкол до конца, а собственный дедлайн (по умолчанию 10 минут) его убивает.
- **`/checks init`** ✅: читает `package.json` scripts, угадывает парсер по
  команде, а по имени — только как fallback, и **печатает** черновик, не записывая
  файл: команда без подтверждения не должна затирать чужой конфиг.
- **Upstream PR в `dsh-tool-lsp`**: сегодня операций четыре (`goToDefinition`,
  `findReferences`, `goToImplementation`, `hover`), диагностик нет. Добавить
  `diagnostics` — и typecheck-петля станет мгновенной без запуска `tsc`.

### Идея 2. Sentry

**Оценка: S–M. Самый дешёвый провайдер: с точки зрения OAuth это копия Atlassian.**

`mcp.sentry.dev/mcp`, DCR, публичный клиент — библиотека из раздела 3 покрывает
это без новых режимов. Значит вся работа — это список тулов, карточки и панель.

**Что сервер отдаёт на самом деле** (снято спайком на живом аккаунте, 20.10.2026).
Топ-левел тулов пятнадцать, и они устроены иначе, чем предполагалось:

- `search_issues` — сгруппированные issues; `query` принимается **на естественном
  языке** (сервер сам переводит его в Sentry-синтаксис), есть `sort`, `period`,
  `limit`. Отвечает **Markdown-документом**, а не JSON, и сам подсказывает
  презентацию: «Cards work well for these issues, with status, assignee, and
  issue ID links visible». `outputSchema` не объявлена — форма ответа видна
  только вызовом.
- `get_sentry_resource` — один ресурс по URL или типу+id (issue, event, trace,
  replay, monitor, snapshot, dashboard). Для issue он отдаёт **тот же документ**,
  что и длиннохвостый `get_issue_details`, то есть отдельный тул для деталей не
  нужен.
- `update_issue` — resolve / reopen / ignore / assign (`status`, `assignedTo` в
  формате `user:<id>` / `team:<id|slug>`, режимы ignore). Это действия панели.
- Длинный хвост (`get_issue_details`, `find_releases`, `get_release_details`,
  `get_issue_user_reports`, `whoami`, …) намеренно **не** вынесен в топ-левел: его
  достают через `search_sentry_tools` + `execute_sentry_tool`.
- `analyze_issue_with_seer` — разбор внешней моделью.

Чего в поверхности **нет**, хотя план это предполагал: тула комментариев и
breadcrumbs в документе issue. Релиз приходит тегом (`release:
storefront@3.0.1`), а не полем «seen in release». Зато есть то, чего план не
ждал: `## Code Location` со ссылкой на файл в GitLab и `## Suspect Commit` с
SHA, автором и **ключом тикета прямо в сообщении коммита** (`DEV-5977: …`) —
готовая связка с Jira из раздела 5.

Панель (по образцу Jira-панели): шапка с issue и окружением, stack trace
код-блоком, теги, ссылки на релиз и коммиты, кнопки Resolve / Ignore / Assign.

Карточки: `sentry_present` — список ошибок с числом событий и трендом;
отдельная карточка «ошибка → подозреваемый коммит → тикет».

Докрутки:

- **Корреляция** с GitLab (suspect commit → MR и автор) и Jira (тикет из
  названия/коммита) — см. раздел 5, это самая ценная связка.
- **Утренний дайджест новых ошибок** — одним вызовом schedule.
- Если MCP отдаёт AI-разбор (Seer), показывать его как **предложение**, а не
  как факт: это внешняя модель, и её текст — не истина.

### Идея 3. GitLab

**Оценка: L. Самый большой объём и самая высокая отдача для ревью.**

Особенности, снятые с живого (проверено): confidential client — секрет из DCR
обязателен; self-hosted инстансы со своим base URL; `device_code` доступен;
скоуп один — `mcp`.

Что даёт: MR (список «на мне» и «ждут моего ревью»), диффы, дискуссии,
пайплайны и логи упавших job, комментарии и approve, issue и board.

**Ревью с CodeRabbit — конкретика.** CodeRabbit пишет замечания ботом-пользователем,
и это превращается в понятный воркфлоу:

1. Дискуссии фильтруются по автору (`coderabbitai[bot]`).
2. Замечания группируются: что просит, где, закрыто ли, что помечено как minor.
3. Агент получает это как список задач: «пройдись по замечаниям и предложи
   правки», а карточка показывает «файл → замечание → предлагаемый патч».
4. Отдельная кнопка — ответить в тред или зарезолвить его.

Осторожно: **резолв треда и ответ — социальные действия**, их стоит делать
только после явного подтверждения, а не «агент решил». Автоправки — да,
автоответы — нет.

Докрутки:

- **`DiffBlock` из UI-кита** для диффа (проверено: компонент есть в
  `dsh-client-ui-primitives`) — рендер диффа в карточке и в панели.
- **Связка с идеей 1**: упавший job → его лог → локальный прогон теми же
  рецептами → карточка «причина и что сделано».
- **Режим ревью**: агент пишет саммари MR (что меняется, что рискует), я
  утверждаю — и оно уходит комментарием.
- **Список «мои MR, где мяч на мне»** — где последнее слово не моё.

### Идея 4. Figma

**Оценка: M–L. Самый экспериментальный пункт.**

Два транспорта: удалённый `mcp.figma.com/mcp` (OAuth, но **DCR закрыт** — клиента
надо заводить руками) и локальный Dev Mode MCP на `127.0.0.1:3845` (без OAuth,
требует запущенного десктоп-приложения). Режим no-auth в библиотеке есть с M1;
локальный транспорт по-прежнему не проверен — приложение не запущено.

**Скриншоты нод.** MCP отдаёт изображения как image-контент; в харнессе есть
сервис attachments и компоненты `ImagePreview`/`ImageLightbox` в UI-ките.
Значит фрейм можно показать в панели. Но: картинка в контексте модели дорогая,
поэтому **агенту — текстовые токены и размеры, человеку — картинку**.
Точный способ отдать картинку в панель — вопрос прототипа (предположение).

**Code Connect** — это маппинги `.figma.ts` в репозитории, связывающие node с
компонентом. Отсюда ценность плагина: собрать в одном месте

- скриншот ноды,
- переменные и стили (то есть токены),
- файл Code Connect для этой ноды,
- наш компонент, на который он указывает.

Сценарий: «возьми фрейм X, найди компонент, сравни отступы и цвета с токенами,
предложи правку». Это и есть «как через Code Connect», только ещё и с диффом.

Докрутки:

- **Design diff**: скриншот фрейма против скриншота реализованной страницы
  (браузерный скриншот можно снять через browser-use подсистему харнесса).
  Сильная вещь, но это отдельный прототип.
- **Генерация CSS-переменных** из переменных Figma.

**Порядок работы здесь — спайк, потом код.** Доступ к Dev Mode есть (решение 4),
но локальный MCP ни разу не проверялся: неизвестны ни список тулов, ни форма
ответа со скриншотом. Значит M6 начинается с получаса работы руками — поднять
Figma Desktop, подключиться к `127.0.0.1:3845/mcp` тем же пробником, которым я
снимал схемы Atlassian, и записать факты. Только после этого имеет смысл писать
транспорт.

Риски: лимиты запросов у Figma MCP (у локального сервера они свои и жёстче);
локальный транспорт живёт только пока открыто приложение; часть данных доступна
лишь на платных местах; скриншоты тяжёлые для контекста модели.

## 5. Идеи сверх четырёх

1. **Одна обвязка для всех провайдеров.** Сейчас панель — это тип вкладки
   Atlassian; с четырьмя плагинами получится четыре почти одинаковых типа.
   Вместо этого — библиотеки `integration-ui` и `integration-host`: первая
   владеет телом панели, карточкой, тулколом, секцией настроек и стилями,
   вторая — конфигом, состоянием входа, роутом и командой; плагин регистрирует
   свой тип вкладки и говорит, что в нём его собственное. Это стоит сделать
   **до GitLab**, иначе копипаста расползётся.
2. **Кросс-корреляция** — то, что нельзя получить, сидя в одном инструменте:
   «ошибка в Sentry появилась в релизе X → коммит Y → MR Z → тикет DQ-66 →
   вот замечания CodeRabbit по этому MR». Это главный аргумент делать всё в
   одном харнессе, а не в четырёх вкладках браузера.
3. **Дайджест** — «что у меня сегодня» одной карточкой. Решено делать с
   настройкой; дизайн — в разделе 5.1.
4. **Pre-push гейт** — связка идей 1 и 3: перед пушем прогнать проверки и
   показать, что именно сломано, до того как это увидит CI.
5. **Upstream-вклад**: OAuth для MCP в стоковый клиент и `diagnostics` в `lsp`.
   Оба меняют экосистему, а не только наш профиль.
6. **Локализация** en/ru/zh через locale-сервис харнесса. Сейчас весь текст
   клиентской половины английский и не проходит через него; для open-source
   это заметный минус.
7. **Market-индекс** — JSON формата 1 на GitHub Pages плюс публикация в npm.
   Без этого «выложить в open-source» не доедет до пользователя: он не сможет
   поставить плагин из UI.
8. **`plugin-build`** — общий `build.mjs` (esbuild + vanilla-extract + обёртка
   клиентского модуля) как devDependency. Сегодня он копипастится в каждый
   новый плагин целиком.
9. **Команда `/work`** — единая точка входа: «что у меня сегодня», «проверь»,
   «открой DQ-66».

### 5.1 Дайджест: что собирать, как настраивать, как доставлять

Решено: дайджест нужен, время и состав настраиваются. Это значит, что кроме
самой карточки нужны три вещи — сборщик, настройка и расписание.

**Сборщик — детерминированный, а не «попросим модель».** Тул `digest` сам
опрашивает провайдеров и строит карточку из того, что они вернули. Причина
простая: дайджест приходит по расписанию, а значит без человека рядом; если он
будет ходить через модель, то в неудачный день придёт выдумка вместо фактов.
Модель подключается поверх и опционально — написать одну вводную фразу, не
трогая данные.

Состав (каждый пункт — переключатель):

| Блок | Источник | По умолчанию |
|---|---|---|
| Задачи в работе и просроченные | Jira | вкл |
| Задачи, назначенные на меня, но не начатые | Jira | вкл |
| MR, где ждут моего ревью | GitLab | вкл |
| Мои MR, где мяч на мне (ответ на ревью, упавший пайплайн) | GitLab | вкл |
| Новые ошибки за сутки | Sentry | вкл |
| Комментарии CodeRabbit за сутки | GitLab | выкл |
| «Вводная фраза от модели» | LLM | выкл |

**Настройка живёт в двух местах** — и это не дублирование, а два разных
сценария:

- **Секция в Settings** (тот же слот, что уже занят Integrations): время,
  дни недели, переключатели блоков, и кнопка «показать сейчас».
- **Команда `/digest`**: `now` — собрать немедленно, `on`/`off` — включить или
  выключить расписание, `blocks …` — состав, `time 09:30` — время. Команда
  пишет в ту же конфигурацию, что и секция; одна настройка, два входа.

**Доставка** — через подсистему `schedule`: расписание создаёт напоминание,
которое приходит в сессию и отдаёт карточку. Время задаётся в локальной зоне;
после простоя приходит только последнее пропущенное срабатывание — это
поведение харнесса, и оно как раз то, что нужно (пять дайджестов за неделю
отпуска не придут).

**Чего дайджест делать не должен:** молча писать в внешние системы. Он только
читает и показывает. Кнопки действий — отдельный шаг с подтверждением.

**Состояние после M7.** Сделаны сборщик, тул, секция настроек, команда и
расписание; шов между дайджестом и интеграциями — реестр источников в
`dsh-integration-host` (см. M7 в разделе 7). Не сделана **вводная фраза от
модели**: сборщик детерминирован по построению, а хост-половине вне турна
неоткуда взять модель, не заведя второй маршрут к ней. Пункт остаётся открытым.

## 6. Сквозные решения и риски

- **Мультиаккаунт в credential-записи** — сделано на M1: ключ записи это
  `scope + instance` (`dsh-gitlab/mcp`, `dsh-gitlab/mcp-work`), старые записи
  читаются как аккаунт `default`, а `instancesOf` перечисляет то, что лежит в
  сторе. Плагины пока держат по одному аккаунту: UI для нескольких — вместе со
  вторым провайдером.
- **Локальный маршрут без аутентификации.** `/dsh-*` сегодня доступен любому
  локальному процессу, и с записью в Jira это уже не только чтение. Варианты:
  общий секрет в заголовке (клиент получает его вместе с бутстрапом) или
  upstream-API харнесса для приватных роутов. Второе честнее, первое быстрее.
- **Кэш и лимиты.** Списки (MR, issue, проекты) кэшировать на десятки секунд,
  уважать `Retry-After`, не долбить API в цикле.
- **Права на запись — решено: социальные действия только с подтверждением.**
  Механически это три уровня, и они не смешиваются:
  1. **Механическое действие** (переход статуса, назначение, resolve) — тул
     вызывается как обычно, а гейтом служит permission-пайплайн харнесса: кто
     хочет строже, ставит соответствующему тулу политику `ask`.
  2. **Социальное действие** (комментарий, ответ в тред, резолв треда ревью,
     approve) — тул требует явного `confirm`, без него возвращает структуру
     «что будет отправлено», а панель показывает кнопку с этим текстом. Так
     формулировка видна человеку **до** отправки, а не после.
  3. **Ничего автоматического по расписанию.** Дайджест и любой scheduled-прогон
     не пишут во внешние системы вообще — только читают; это зафиксировано в 5.1.
  Причина такой строгости: комментарий в чужом MR — это не состояние задачи, а
  репутация, и отменить его нельзя.
- **Версионирование.** Монорепа + changesets; `engines.dsh` у каждого бандла;
  библиотеки — обычные semver-зависимости.
- **Тесты.** У библиотеки три набора: чистые решения (`test/unit.ts`), бридж
  против локального MCP-сервера (`test/bridge.ts`) и живой conformance
  (`test/conformance.ts`). У devkit — четыре офлайновых: парсеры на записанных
  потоках, конфиг и черновик, раннер (часть проверок гоняет настоящие команды) и
  тул с валидатором карточки. У плагина — свой dry-run на 100 проверок. Фикстуры
  MCP на каждый парсер — по мере появления провайдеров.
- **Приватность.** Токены не попадают в логи и в контекст модели; в карточки —
  только то, что нужно человеку.

**M0 сделана** (20.10.2026): монорепа на `packages/atlassian` и `packages/mcp-oauth`,
плагин переименован в `dsh-atlassian-plugin` и работает на библиотеке; библиотека
проходит discovery против пяти живых эндпоинтов (Atlassian v1/v2, Sentry, GitLab,
Figma) — это `packages/mcp-oauth/test/conformance.ts`.

**M1 сделана** (20.10.2026), но не в том виде, в каком задумывалась. Сделано:

- **Мультиаккаунт.** Ключ записи — `scope + instance`: `dsh-gitlab/mcp` для
  аккаунта по умолчанию, `dsh-gitlab/mcp-work` для названного. Прежние записи
  читаются как `default`, переносить нечего. `instancesOf` отвечает, какие
  аккаунты лежат в сторе; профиль несёт `instance`, поэтому два аккаунта одного
  провайдера различимы и в логах.
- **No-auth.** У профиля появился необязательный блок `oauth`: без него бридж
  строит транспорт без `authProvider` и не требует записи вообще.
- **Conformance.** Один прогон на пять живых эндпоинтов: discovery, DCR,
  проверка клиента на token endpoint (в том числе контрольным несуществующим
  клиентом, чтобы было видно, что ответ вообще что-то значит) и authorize URL,
  который должен отрендериться. Отдельно — confidential-путь обеими формами
  (`client_secret_post` и `client_secret_basic`) против Atlassian v1 с контролем
  на неверный секрет. 55 проверок, все зелёные.
- **Политика клиента.** `discover` читает `token_endpoint_auth_methods_supported`
  и выбирает метод регистрации (публичный клиент, когда сервер его допускает),
  а решает всё равно ответ: GitLab на запрос секрета отвечает публичным клиентом.

Не сделано и почему: **device flow** — эндпоинт не объявлен в метаданных, а
единственный известный отвечает отказом клиенту из DCR (см. раздел 3);
**confidential-путь на GitLab и Figma** — невозможен по факту: GitLab выдаёт
публичного клиента, Figma закрывает регистрацию для анонимных вызовов. Критерий
M1 в исходной формулировке («GitLab-сессия поднимается с секретом из DCR»)
выполнить нельзя, и это записано как факт, а не как долг. Из-за закрытого DCR у
Figma в план вернулся manual-client режим (решение 3) — он нужен на M6.

**M2 сделана** (20.10.2026): пакет `packages/devkit` (`dsh-devkit-plugin`).
Рецепты живут в `dsh-checks.json` в корне проекта — файл этого репозитория и есть
рабочий пример; тул `checks` принимает имя рецепта или `all` и никогда команду,
запускает всё через `ctx.shell` (тот же сиам, на котором стоит `bash`) и отвечает
одним структурным результатом на рецепт. В UI — строка тулкола и карточка в хвосте
ответа, где каждая неудача это `file:line`, открывающий файл в панели харнесса.
Парсеры: `tsc`, `biome` (JSON- и pretty-репортеры), `eslint`, `vitest`, `jest`,
`pytest`, `generic`. Плюс `/checks` (список рецептов) и `/checks init` (черновик из
`package.json`, который печатается, а не пишется).

Что выяснилось по ходу и чего в плане не было:

- **Потоки разделяются.** Biome печатает диагностики в stderr, а счётчики — в
  stdout; раннер читает оба и берёт счётчик как максимум из двух, чтобы поток,
  который лишь повторяет число, его не удваивал.
- **`generic` нужен чаще, чем казалось.** Пока формат не разобран, честный
  результат — код возврата плюс хвост вывода, и именно он виден в карточке.

Осталось из докруток идеи 1: **watch-режим**, **длинные прогоны через
`ctx.jobs`**, парсеры `cargo`/`go test` (писать их здесь не на чем — ни cargo, ни
go не установлены, а сочинять формат по памяти репозиторий не берётся) и
**upstream-`diagnostics` в `dsh-tool-lsp`**. Клик по файлу открывает его начало:
сиденье `conversation.chat.turnTail` отдаёт `openFile(path)` без строки, а
строка есть только у сиденья тулкола.

**M3 сделана** (20.10.2026): пакет `packages/sentry` (`dsh-sentry-plugin`) —
первый провайдер на библиотеке. OAuth-профиль Sentry, `/sentry
status|login|logout|sync`, секция **Sentry** в Settings, карточка `sentry_present`
в хвосте ответа и панель issue в правом Sidebar с Resolve / Ignore / Reopen /
Assign. 61 проверка в пакете: ридеры Markdown, панель и карточный тул с фейковым
мостом, роут и конфиг.

Спайк на живом аккаунте оказался обязательным — и именно потому, что
поверхность оказалась не такой, как в плане (см. идею 2). Что дал спайк:

- Сервер отвечает **Markdown'ом**, а не JSON, и сам предлагает презентацию
  карточкой. Поэтому карточка и панель читают документ: ридеры живут в
  `src/host/presentation/parse.ts`, а `test/parse.ts` закрепляет их **реальными
  захватами** (идентификаторы заменены — захват снят с живого аккаунта).
- Детали issue отдаёт топ-левел `get_sentry_resource`, и это **тот же документ**,
  что и длиннохвостый `get_issue_details`: отдельный тул для деталей не нужен, а
  значит панель не зависит от `execute_sentry_tool`.
- Запись проверена, не меняя данных: `update_issue` с несуществующим id проходит
  схему и аутентификацию и получает от API 404 — имена аргументов и путь записи
  верны. Сама мутация на живом не проверялась: резолвить чужую issue без спроса
  нельзя.
- `search_issues` принимает запрос **на естественном языке** — сервер переводит
  его сам, своим агентом. Поэтому `sentry_present` может передать вопрос
  пользователя почти дословно.
- Suspect commit несёт **ключ тикета в сообщении коммита** (`DEV-5977: …`) —
  связка с Jira из раздела 5 приходит бесплатно, осталось её отрисовать (M8).

Побочно: в библиотеке `mcpJson` не читал `structuredContent`, хотя docstring это
обещал; теперь читает и ставит его первым — Sentry присылает именно его для
`find_organizations`, `find_projects` и `search_sentry_tools`. И dry-run
Atlassian ждал authorize URL шесть секунд, чего на медленной сети не хватает
(discovery + DCR — живые вызовы): теперь ждёт тридцать.

Осталось из идеи 2: корреляция с GitLab и Jira (M8) и Seer — его разбор в
карточку не выводится вовсе; если выводить, то как предложение внешней модели, а
не как факт. Утренний дайджест сделан на M7 — блок новых ошибок приходит из этого
пакета через реестр источников.

**M5 сделана** (20.10.2026): пакет `packages/gitlab` (`dsh-gitlab-plugin`).
Реализованы обе половины: тул `gitlab_present` (карточка MR-списка, замечаний
ревью и упавших job), панель merge request в правом Sidebar с четырьмя
секциями — Overview, Diff, Discussions, Pipeline, — тул `gitlab_review`
(комментарий, ответ в тред, resolve/reopen, approve/unapprove) и лог упавшего
job. 113 офлайновых проверок в пакете: конфиг, запись токена, ридеры,
панель/тулы/роут против поддельного канала, и гейт подтверждения.

**Транспорт — не MCP, и это главное отличие от плана.** Роадмап предполагал
GitLab на библиотеке `dsh-mcp-oauth`; M5 началась именно так, и OAuth-путь
заработал: DCR выдал публичного клиента, PKCE, consent, токен со скоупом `mcp`.
Дальше живой эндпоинт ответил `403 Forbidden - MCP server not enabled for any of
your groups`: доступ к MCP-серверу включается на уровне top-level группы, а
владельца такой группы у пользователя нет. Вторая половина той же стены —
скоуп: токен MCP принимается **только** на `/api/v4/mcp`, для REST он даёт `401`,
а единственный объявленный скоуп — `mcp`. Решение (принято с пользователем):
ходить в REST API личным токеном, который у пользователя уже есть, а
MCP-половину из плагина убрать. Библиотека `dsh-mcp-oauth` остаётся тем, чем и
была, — фундаментом Atlassian и Sentry.

Что из этого следует для репозитория:

- **`dsh-integration-host` переиспользован без изменений** — нормализация патча,
  состояние, роут, слэш-команда и документ статуса. `IntegrationAuthFace`
  оказался достаточным контрактом для входа по токену: `GitLabAuth` реализует
  его, `signIn()` отвечает «вставьте токен в карточку», а `saveToken()` —
  то, что этот вход добавляет к общему лицу. `IntegrationAuth` из библиотеки —
  это OAuth-реализация того же контракта, а не единственная.
- **`dsh-integration-ui` получила поле вводимого секрета.** Карточка настроек
  была устроена вокруг браузерного входа; теперь `SettingsSectionSpec` — это
  объединение двух форм (браузерная и токенная), и вторая рисует `Input` +
  Save/Forget. Тип не даёт собрать карточку, у которой есть и кнопка входа, и
  поле: это альтернативы, а не опции.
- **`dsh-mcp-oauth` получила одно небольшое дополнение, и оно осталось**:
  `McpBridge.lastFailure` — причина, по которой соединение не поднялось. Ровно
  этот 403 был виден только в логе хоста, а карточка показывала «не подключено»;
  теперь причина доходит до настроек у всех интеграций, и это закреплено тестом
  с сервером, который отказывает.
- **Запись токена — `dsh-gitlab/token`.** `credentialKeyFor` из `mcp-oauth`
  строит id только вида `mcp`/`mcp-<instance>`, потому что он про аккаунты
  OAuth; для записи не-OAuth хватает `credentialKey(scope, id)` из
  `dsh-credentials` напрямую.

Что дал живой захват (аккаунт пользователя, 20.10.2026): ридеры проверены на
настоящих ответах `merge_requests`, `merge_requests/:iid`, `/diffs`,
`/discussions`, `/pipelines`, `/pipelines/:id/jobs`, `/jobs/:id/trace` — панель
открывает реальный MR на 5 файлов и 4 треда, роут job отдаёт 64 КиБ хвоста
лога, который кончается на `ERROR: Job failed: command terminated with exit
code 1`. Три факта, которых план не знал:

- **Статистики по файлу в `/diffs` нет** — есть только текст патча; `+N/−M` в
  шапке файла считаются из самого патча.
- **Состояние треда в `/discussions` лежит на заметках**, а не на треде:
  `resolvable`/`resolved` у заметки, `resolvable` у треда. Тред считается
  закрытым, когда закрыты все его разрешимые заметки.
- **Фильтр «Bots» по имени не работает.** Реальный CodeRabbit пишет под
  обычным аккаунтом (`code_rabbit_dogedev`), а `bot`-флаг GitLab отдаёт в
  списке MR и не отдаёт в дискуссиях. Поэтому в панели фильтр не по автору, а
  по сути: **Findings** — треды с заметкой на строке диффа, ровно те, что
  попадают в карточку. Флаг `bot`, когда он есть, сохраняется и рисуется
  тегом, но ничего по нему не фильтруется.

Не сделано и почему: **карточка списка MR не показывает пайплайн** — листовой
эндпоинт GitLab не отдаёт `head_pipeline`, а дотягивать его по строке значило бы
N запросов на карточку; **ретрай упавшего job** из панели — механическое
действие, которое просится следующим (M8), но в критерий M5 не входило;
**мультиаккаунт** — ключ записи один (`dsh-gitlab/token`), второй аккаунт
потребует того же `instance` в ключе, что и у OAuth-провайдеров.

**M4 сделана** (20.10.2026): две библиотеки, `packages/integration-host`
(`dsh-integration-host`) и `packages/integration-ui` (`dsh-integration-ui`),
и три плагина на них. Хостовый каркас: нормализация патча эндпоинта, состояние
входа, роут настроек и слэш-команда — всё это было написано дважды дословно;
теперь провайдер даёт имя, лог-тег, чтение своих account-фактов (Sentry —
организация, Atlassian — сайт) и свои пути роута. Браузерный каркас: тело
панели с загрузкой, ошибкой, повтором и записью, карточка хода, терсный тулкол,
секция настроек, транспорт к хосту и общий стилевой лист. Плагин регистрирует
свой тип вкладки и говорит, что в нём его собственное.

Что решили по ходу:

- **Тип вкладки — свой у каждого провайдера.** Роадмап хотел один общий kind с
  реестром провайдеров, но клиентские половины плагинов — отдельные бандлы с
  инлайн-библиотекой внутри, и общего рантайма у них нет: реестр пришлось бы
  держать в root-контексте, а владение типом — на одном из плагинов. Взяли
  общий *код* и свой kind (`atlassian`, `sentry`): панели можно держать рядом,
  кросс-плагинного состояния нет.
- **`kind` — это контракт вкладки, и он объявляется плагином.** Библиотека
  отдаёт фабрику определения и опенер, типизированный через
  `SidebarRightTabParamsMap`; сам `declare module` с целевым типом остаётся в
  плагине, потому что ключ карты — его.
- **Стили переехали в библиотеку одним `.css.ts`**, который плагин
  ре-экспортирует. vanilla-extract компилирует каждый `*.css.ts` своим
  esbuild-прогоном и не пробрасывает туда `alias` — поэтому в build.mjs каждого
  плагина есть резолвер рабочего пространства: без него shared-стили
  разворачивались бы из собранного `lib/` и тянули в бандл вторую копию
  vanilla-extract runtime (это видно по `setAdapter` в бандле — проверка ниже).
- **Карточка отдаёт владельцу сиденья себя целиком.** `checks` кликает по файлу
  из хвоста ответа, а `openFile` живёт в пропсах сиденья, не в payload — поэтому
  провайдер карточки получает props вторым аргументом, а не только свой payload.

Проверки: 26 в `integration-host` (конфиг, обучение account-фактам, роут,
команда), 12 в `integration-ui` (машина состояний карточки), 61 в Sentry,
100 в Atlassian, 95 в devkit. Плюс аудит бандлов: клиентский `require` — только
`react`, `react/jsx-runtime` и UI-кит; `setAdapter` в бандлах нет.

Порядок неслучаен: **M0–M1 до всех интеграций** (иначе три раза переписывать
одно и то же), **M4 сделана до GitLab** — иначе панель размножилась бы, — **M2 независим**
(можно делать в любой момент или вообще заморозить). **M6 начинается со спайка,
а не с кода**: локальный транспорт Figma не проверен ни разу, и писать под него
вслепую — это ровно тот случай, когда неделя уходит на переписывание.

**M6 сделана** (21.10.2026): пакет `packages/figma` (`dsh-figma-plugin`).
Спайк сделан первым и оказался ровно тем, чем задумывался: полчаса на живой
`127.0.0.1:3845/mcp` дали список тулов и формы ответов, после чего код писался по
фактам, а не по догадкам. Транспорт — **только локальный**, и это решение
пользователя по фактам из спайка (см. ниже).

Что сервер отдаёт на самом деле (снято с живого приложения 21.10.2026). Десять
тулов: `get_design_context`, `get_variable_defs`, `get_screenshot`,
`get_motion_context`, `get_code_connect_map`, `add_code_connect_map`,
`get_code_connect_suggestions`, `send_code_connect_mappings`, `get_metadata`,
`get_figjam`. Плюс три промпта и ни одного ресурса. Формы ответов, на которых
стоит панель:

- **`get_metadata` отвечает XML**, а не JSON: `<frame id="960:6938" name="Menu
  Items" x="14096" y="2243" width="260" height="502">` и вложенные элементы, где
  имя элемента — это тип слоя (`frame`, `symbol`, `text`, `canvas`). После
  закрывающего тега сервер дописывает абзац-совет агенту («MUST call
  get_design_context»), и он не часть документа. С `nodeId` страницы ответ на
  163 КиБ — это вся страница, поэтому панель читает корень и его прямых детей.
- **`get_variable_defs` отвечает плоским объектом** `{name: value}`, где значение
  — то, как Figma его рендерит: `"8": "8"`, `"text/primary": "#ffffff"`,
  `"Body/M/Regular": "Font(family: \"Inter\", …)"`. Токен-строка, а не структура.
- **`get_code_connect_map` отвечает объектом, ключ по node id**, и `{}` для ноды
  без маппинга; поля — `codeConnectSrc` и `codeConnectName`.
- **`get_screenshot` отвечает image-блоком** (`type: "image"`, `mimeType`,
  base64 `data`), а `get_design_context` — React+Tailwind кодом и **тем же
  скриншотом внутри**. Отсюда решение панели: картинку брать отдельным тулом.
- **Выделения как отдельного тула нет.** «Текущее выделение» резолвится тем же
  `get_metadata` без `nodeId`: с выделением он отвечает XML и корнем называет
  выбранную ноду, без выделения — прозой со списком страниц документа. Это и
  стало признаком «ничего не выбрано».

Что решили по ходу:

- **Агенту — текст, человеку — картинку.** `figma_present` отвечает модели
  фактами (тип, размер, переменные, Code Connect, дети), а скриншот в результат
  не кладёт вовсе; в описании тула сказано, каким тулом сервера посмотреть
  дизайн самому. Причина та же, что в идее 4: картинка в контексте модели дороже
  чисел рядом с ней, а панель человек всё равно видит.
- **Скриншот идёт своим роутом, а не через документ панели.** `RouteContext`
  библиотеки получил `sendBytes`: картинка не помещается в JSON, которым
  описывается сама себя, и `<img>` тянет её из `/dsh-figma/screenshot?node=…`
  (с `rev`, чтобы перезагрузка документа перезапрашивала кадр). Проверено на
  живом: 11 489 байт PNG на страницу.
- **Панель открывается сама, но только на живой вызов.** Строка тулкола помнит,
  что видела вызов в фазе «выполняется», и на переходе в «результат» навигирует
  правый Sidebar на ноду; вызов, отрисованный из лога сразу settled, не двигает
  ничего — прокрутка истории не должна переставлять панели.
- **У карточки настроек появилась третья форма.** `SettingsSectionSpec` был
  объединением двух (браузерный вход и поле для секрета); локальному серверу не
  подходит ни одна, поэтому `credentials: "none"` — карточка только сообщает
  состояние и называет переключатель, который надо включить.
- **Три копии разбора аргументов тулкола съехались в библиотеку.** `blockArgs`
  в `dsh-integration-ui`; gitlab, sentry и devkit больше не держат своих версий.
  Заодно `itemTitle` и `tabs` переехали из стилей GitLab в общий лист — их
  затребовал второй плагин.
- **`RuntimeState` получил значение типа по умолчанию.** У интеграции без
  аккаунта (локальный сервер) нет фактов, и заводить пустой класс ради
  параметра типа было бы шумом.

**Remote-транспорт не сделан, и это факт, а не долг.** Замерено на живом:
`registration_endpoint` (`https://api.figma.com/v1/oauth/mcp/register`) отвечает
`403 Forbidden` анонимному `POST`, метаданные AS объявляют единственный скоуп
`mcp:connect`, а документация Figma говорит, что подключаться могут только
клиенты из их каталога, для новых — waitlist. Режим manual client из решения 3
потребовал бы Figma-приложения со скоупом, которого в списке скоупов REST-приложения
нет; писать его вслепую — это код, который нельзя проверить. Шов оставлен: профиль
просто без блока `oauth`, и добавить второй транспорт — это профиль плюс выбор в
конфиге.

Не сделано и почему: **Code Connect не проверен на живом** — в файле пользователя
нет ни одного маппинга (проверены 60 нод страницы Components, все `{}`), так что
читатель закреплён синтетической фикстурой по документированной форме, а панель
честно говорит «No Code Connect mapping names this node»; **запись маппингов**
(`add_code_connect_map`, `send_code_connect_mappings`) не выведена в панель — это
запись в чужой файл и отдельное решение; **design diff** (скриншот фрейма против
скриншота реализации) остался докруткой идеи 4.

**Первый запуск в приложении дал баг, которого не было видно ни в одном тесте.**
После перезапуска харнесса карточка настроек сказала «The Figma host half is not
reachable», хотя хост-половина работала: её тулы (`figma_present` и десять
`mcp__figma__*`) были зарегистрированы, а роут `/dsh-figma/status` отвечал `404`.
Причина оказалась в гонке, а не в коде плагина: `ctx.get("webServer")` возвращает
сервис, только когда фибра его провайдера **активна** (`cordis/lib/reflect.ts`,
`_getImpl`), а строка `webserver` монтируется поздно — её конфиг ждёт `webStartup`,
тот ждёт `cmdlineArgs` из слоя самого приложения. Плагин, который просто спросил
сервис в `apply`, получает `undefined` и молча остаётся без роута. Atlassian,
Sentry и GitLab выиграли эту гонку случайно — у них тот же код.

Лечение: `mountIntegrationRoute(ctx, { prefix, handler })` в `dsh-integration-host`
регистрирует роут через `ctx.inject(["webServer"], scoped => …)` — то есть ждёт
сервис и снимает роут вместе с ним. Четыре копии одного и того же блока уехали в
библиотеку, и там же появилась проверка на этот сценарий: она монтирует роут
*раньше* слушателя и убеждается, что он доезжает, когда слушатель появляется.
Урок общий и записан в AGENTS.md §6: необязательный сервис берётся через scoped
`ctx.inject`, а не через `ctx.get` в момент активации.

Проверки: 36 в `packages/figma` на читателях (XML, переменные, Code Connect,
node id и ссылки, картинка), 35 на панели, туле и роуте против поддельного моста,
15 живых против запущенного десктоп-приложения (пропускаются, если оно не
запущено). Плюс аудит бандлов: клиентский `require` — только `react`,
`react/jsx-runtime` и UI-кит; `setAdapter` в бандле нет.

**M7 сделана** (21.10.2026): пакет `packages/digest` (`dsh-digest-plugin`) плюс
по одному файлу-источнику в Atlassian, Sentry и GitLab.

Главный вопрос M7 был не «как собрать карточку», а **как дайджесту вообще узнать
чужие данные**. Три интеграции не могут импортировать друг друга — у каждой своя
пара бандлов и свой читатель, — а ходить в `ctx.tools` за чужими тулами значит
знать их имена и разбирать их сырые ответы: ровно та скрытая связность, против
которой написан §5.3. Поэтому шов сделан явным:

- `dsh-integration-host` объявляет, **что такое источник дайджеста** — блок с
  заголовком, переключателем по умолчанию и загрузчиком, — и владеет реестром
  `DigestSources`;
- `dsh-digest-plugin` **предоставляет** реестр как `ctx.digestSources`;
- каждая интеграция **регистрирует** в нём свои блоки через scoped
  `ctx.inject([DIGEST_SOURCES], …)`.

Это тот же приём, что у `mountIntegrationRoute`: регистрация ждёт сервис и
снимается вместе с ним, поэтому **порядок загрузки не важен**, а сборка без
плагина дайджеста просто не будит висящую фибру. Проверено в
`packages/integration-host/test/unit.ts`: источник грузится раньше реестра,
дожидается его и появляется в списке; повторный id блока отвергается; снятие
фибры источника убирает его блок, снятие плагина — сам сервис.

Что решили по ходу:

- **Заголовок и переключатель блока едут от провайдера, а не лежат в дайджесте.**
  Карточка настроек рисуется по тому, что установлено: поставили интеграцию —
  появился её блок с её же умолчанием, убрали — блок исчез. Список блоков не
  хранится нигде вторым экземпляром.
- **Сбой одного блока — это строка `unavailable` у этого блока.** «На ревью
  ничего не ждёт» и «GitLab не подключён» — разные факты, и карточка их не
  смешивает; дайджест при этом не падает целиком.
- **Окно — сутки, и это сказано в заголовке блока.** Недельный дайджест всё
  равно смотрит на последние 24 часа, поэтому блок называется «New errors in the
  last 24 hours», а не обещает неделю.
- **Расписание сессионное, и это не обходится.** Сервис `ctx.schedule` хранит
  напоминание за той сессией, которая его создала, и доставляет туда же. Значит
  секция настроек владеет *что* и *когда*, а *где* — только `/digest on`,
  набранный в нужной сессии; карточка так и говорит. Смена времени при этом
  пересоздаёт напоминания **всех** сессий (через `catalog()`), иначе карточка
  правила бы значение, которое прочитает лишь следующий `/digest on`.
- **Семь дней — это `daily`, меньше — `weekly`.** У сервиса два правила
  повторения, и «эти дни недели, кроме всех» среди них нет; выбор между ними
  живёт в одной чистой функции, а JS-нумерация дней переводится в ISO (`вс` → 7).
- **Настройки — один JSON под домашней директорией харнесса.** У дайджеста нет
  ни аккаунта, ни credential-записи, к которой их подшить, а `ctx.storage` — хаб
  бэкендов, а не key-value. Файл читается прощающе: опечатка, чужой блок,
  несуществующая зона падают в умолчание, а не в отказ, и запись идёт через
  rename, чтобы падение не оставило половину документа.
- **Напоминание опознаётся по маркеру в промпте**, а не по заголовку: задача
  пользователя с тем же названием не должна попасть под удаление.
- **Тул `digest` не принимает аргументов.** Состав дайджеста — это настройка;
  тул, который сужает его по вызову, давал бы разный дайджест каждое утро.
- **`dsh-integration-host/digest` — третий вход библиотеки.** Клиентской половине
  нужен только тип строки, и он не должен тянуть node-код роута в браузерную
  программу: у библиотеки теперь три входа по той же причине, что и раньше два.

Чего не сделано и почему:

- **Вводной фразы от модели нет.** Раздел 5.1 называет её опциональной;
  сборщик детерминирован, а хост-половине вне турна неоткуда взять модель, не
  заводя второй маршрут. Пункт остаётся в 5.1 как незакрытый.
- **Корреляции между провайдерами нет** — это M8. Дайджест показывает то, что
  ответил каждый источник, и не утверждает, что ошибка Sentry пришла из
  конкретного MR.
- **Живой проверки нет ни одной.** Все три источника покрыты офлайн, на
  записанных формах ответов; на живых аккаунтах дайджест не запускался.

Проверки: 39 в `packages/integration-host` (к ним добавились восемь на реестр
источников), 98 в `packages/digest` (настройки и их файл, расписание против
поддельного сервиса, правило сборки и изоляция сбоев, грамматика `/digest`),
14 в `packages/atlassian`, 13 в `packages/sentry`, 22 в `packages/gitlab` — по
одному новому файлу на интеграцию, поверх прежних. Плюс аудит бандлов: клиентский
`require` — только `react`, `react/jsx-runtime` и UI-кит; `setAdapter` в бандлах
нет; хост-половина дайджеста не тянет `dsh-session` и `dsh-llm`.

## 8. Решения (приняты)

1. **Монорепа.** Общие библиотеки — workspace-зависимости, релизы — changesets.
2. **Без скоупа, имена по принципу `dsh-...-plugin`.** Проверено по реестру npm:
   `dsh-atlassian-plugin`, `dsh-gitlab-plugin`, `dsh-sentry-plugin`,
   `dsh-figma-plugin`, `dsh-devkit-plugin`, `dsh-workflow-plugin`,
   `dsh-mcp-oauth`, `dsh-integration-ui`, `dsh-plugin-build` — **все свободны**
   (контроль: `react` отдаёт 200, они — 404). Библиотеки суффикса `-plugin` не
   получают: пакет без `dsh.bundle` харнесс трактует именно как библиотеку, и
   это честнее для того, кто читает `package.json`.
3. **Только gitlab.com.** Значит для GitLab manual-client режим не нужен: его
   DCR выдаёт публичного клиента, и этого хватает. Но у Figma анонимный DCR
   закрыт (403), поэтому режим «client_id/secret вводит пользователь» нужен на
   M6 — иначе Figma не подключить вовсе. Остаётся вопрос, делать его в
   библиотеке или отдельным пакетом-расширением. **Уточнено на M5:** вход в
   GitLab — личный токен и REST, а не OAuth: MCP-эндпоинт выключен на уровне
   группы, а его скоуп `mcp` для REST не годится (см. раздел M5).
4. **Figma Dev Mode есть, приложение просто не запущено.** Локальный транспорт
   без OAuth — в объёме M6, и в план добавлен отдельный спайк: поднять Figma
   Desktop, снять схему локального MCP и только после этого писать код.
5. **Дайджест делаем, с настройкой** — время и состав. Дизайн в разделе 5.1.
6. **Социальные действия — только с подтверждением.** Механика зафиксирована в
   разделе 6.
7. **Пока библиотекой.** Апстрим в DSH — отдельным решением позже; public
   conformance-набор из M1 и есть аргумент для него.
8. **Общий код, свой тип вкладки на провайдера** (M4). Один kind с реестром
   провайдеров требовал бы общего рантайма у бандлов, которых у них нет; вместо
   этого библиотека владеет телом панели, а плагин объявляет свой kind и свой
   `SidebarRightTabParamsMap`. Панели разных интеграций можно держать рядом.
9. **Хостовый каркас — тоже библиотека** (M4). `dsh-integration-host` владеет
   тем, что одинаково у всех: патч эндпоинта, состояние входа, роут настроек,
   слэш-команда. Провайдер приносит только своё — профиль, факты аккаунта, пути
   роута и панель.
10. **Figma — только локальный транспорт** (M6, решение принято с пользователем).
    Удалённый `mcp.figma.com/mcp` закрыт для сторонних клиентов: анонимный DCR
    отвечает `403`, единственный скоуп `mcp:connect` не значится среди скоупов
    REST-приложения, а документация пускает только клиентов из каталога Figma.
    Manual-client режим из решения 3 поэтому не делался: он был бы кодом, который
    нельзя проверить. Шов оставлен — профиль без блока `oauth`.
11. **Дайджест собирается через реестр источников** (M7). Интеграция не может
    импортировать другую, а разбирать чужие тулы по именам — скрытая связность,
    поэтому контракт источника живёт в `dsh-integration-host`, реестр
    предоставляет плагин дайджеста, а интеграции регистрируют в нём свои блоки
    через scoped `ctx.inject`. Заголовок и умолчание блока едут от провайдера:
    карточка настроек рисуется по установленному, а не по списку в одном месте.
12. **Расписание дайджеста привязано к сессии** (M7, решение принято с
    пользователем). Сервис `ctx.schedule` хранит напоминание за создавшей его
    сессией и доставляет туда же, поэтому *что* и *когда* задаёт секция настроек,
    а *где* — `/digest on` в нужной сессии. Смена времени пересоздаёт напоминания
    всех сессий, а не только той, где её поменяли.

## 9. Что ещё не решено

- **Аутентификация локального маршрута.** Секрет в заголовке (быстро) или
  upstream-API харнесса для приватных роутов (честно) — см. раздел 6. С M7 к
  списку таких роутов добавился `/dsh-digest`.
- **Вводная фраза от модели в дайджесте.** Сборщик детерминирован, и хост-половине
  вне турна неоткуда взять модель, не заведя отдельный маршрут к ней. Пока не
  заведён — пункт раздела 5.1 остаётся открытым.
- **Живой прогон дайджеста.** Все три источника покрыты офлайн, на записанных
  формах ответов; на живых аккаунтах дайджест не запускался ни разу.
- **Куда класть market-индекс** — GitHub Pages репозитория или отдельная репа
  `dsh-plugins`. Влияет только на M8.
- **Удалённый транспорт Figma** — вернуться, если Figma откроет динамическую
  регистрацию или добавит `mcp:connect` в скоупы OAuth-приложения. Тогда это
  профиль с `oauth` плюс выбор транспорта в конфиге, а не переписывание.
