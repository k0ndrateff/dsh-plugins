# План развития

Как разложены плагины, что измерено на живых эндпоинтах и что делать дальше.
Обозначения: **проверено** — снято с живого сервера или из кода харнесса;
**предположение** — гипотеза, требующая прототипа.

Состояние на 24.10.2026: 14 пакетов, 214 тестов; `dsh-browser-plugin` в B4. Сделаны M0–M8, идёт M9 (агентский
браузер): B0–B3 закрыты, живой вьюпорт работает и принимает ввод, остался B4, см.
[browser.md](browser.md).

---

## 1. Что уже есть

| Слой | Состояние |
|---|---|
| OAuth для MCP | RFC 9728 (PRM), RFC 8414 (AS metadata), RFC 7591 (DCR), PKCE S256, loopback с подбором порта, refresh под кросс-процессным локом, запись в credential-стор, мультиаккаунт, профиль без OAuth |
| Мост к MCP | свой транспорт с `authProvider`; обнаруженные тулы публикуются штатным адаптером харнесса |
| UI | карточка в хвосте ответа (`presentationMeta`), панель в правом Sidebar (свой kind на провайдера), терсные тулколы, одна страница Integrations в настройках |
| Сборка | `dsh-plugin-build`: esbuild на обе половины, vanilla-extract с инлайном CSS, обёртка клиентского модуля |
| Связи между пакетами | два реестра — `digestSources` и `correlationSources`; интеграция регистрирует в них блок или адаптер через scoped `ctx.inject` |
| Браузер (M9) | `dsh-browser-plugin`: пять тулов, `/browser`, свой браузер на каждый разговор и живой вьюпорт в правой панели — с лентой команд, кликами, клавишами, историей, размером страницы, настройками из схемы и чипом возврата в панель, 61 тест; B4 в работе — остались политика доменов и релиз |

Главный вывод: дорогая часть — не интеграция, а OAuth и мост. Поэтому они
библиотека, а каждый новый провайдер — это «профиль + список тулов + UI».

## 2. Структура и почему так

Монорепа, пакеты в `packages/`. Плагин (то, что ставит пользователь) — npm-пакет
с `dsh.bundle.patch`; библиотека — npm-пакет без него.

```
packages/
├── mcp-oauth/        dsh-mcp-oauth          библиотека: OAuth для MCP
├── integration-host/ dsh-integration-host   библиотека: хостовый каркас
├── integration-ui/   dsh-integration-ui     библиотека: обвязка UI
├── plugin-build/     dsh-plugin-build       библиотека: общий build.mjs
├── devkit/           dsh-devkit-plugin      бандл: рецепты проверок
├── atlassian/        dsh-atlassian-plugin   бандл: Jira и Confluence
├── sentry/           dsh-sentry-plugin      бандл: ошибки Sentry
├── gitlab/           dsh-gitlab-plugin      бандл: MR, ревью и пайплайны
├── figma/            dsh-figma-plugin       бандл: фрейм, токены, Code Connect
├── digest/           dsh-digest-plugin      бандл-мета: дайджест
├── correlation/      dsh-correlation-plugin бандл-мета: цепочка через интеграции
├── integrations/     dsh-integrations-plugin бандл: страница Integrations
└── workflow/         dsh-workflow-plugin    бандл-мета: патч, подключающий остальные
```

**Проверено:** bundle — npm-пакет с `dsh.bundle.patch`, то есть слой конфигурации,
который вставляет строки плагинов. Profile — директория
`~/.dsh/profiles/<name>` со списком бандлов, а установка делегирует в pnpm в
директории профиля: единица распространения — npm-пакет. Market — JSON формата 1,
который пользователь добавляет источником; каждый плагин в нём ставится,
обновляется и удаляется по отдельности.

Почему не один большой плагин: версия была бы одна на всех (правка в Figma
выпускает релиз Jira-панели); зависимости не разделяются; выключить по частям
нельзя; пакет на 5000 строк просматривается вместо ревью. Почему не четыре
репозитория: общий код пришлось бы копировать или публиковать на каждую правку.

Компромисс «хочу всё сразу» — `dsh-workflow-plugin`: он зависит от восьми бандлов
и патчем подключает их строки, не содержа при этом кода. Ставить его надо
**вместо** отдельных бандлов: два слоя с одной строкой `id` — дубль.

Имена пакетов — без скоупа, по принципу `dsh-...-plugin` у бандлов; библиотеки
суффикса не получают, потому что пакет без `dsh.bundle` харнесс и так трактует
как библиотеку.

## 3. Что измерено на живых провайдерах

### 3.1 OAuth

| Провайдер | Ресурс | AS | DCR | PKCE | Что выдаёт DCR |
|---|---|---|---|---|---|
| Atlassian | `mcp.atlassian.com/v1\|v2/mcp` | `mcp.atlassian.com` | да | S256 | v1 — public (`none`); v2 кладёт в ответ ещё и секрет |
| Sentry | `mcp.sentry.dev/mcp` | `mcp.sentry.dev` | да | S256 | public (`none`) |
| GitLab | `gitlab.com/api/v4/mcp` | `gitlab.com` | да | S256 | **public (`none`)** — запрошенный метод игнорируется |
| Figma | `mcp.figma.com/mcp` | `api.figma.com` | **нет** | S256 | анонимный `POST` на register — 403 |

Детали:

- **Atlassian v1 и Sentry**: `none` даёт публичного клиента без секрета, а
  `client_secret_post|basic` — секрет. Оба метода прогнаны против живого token
  endpoint: верный секрет — `invalid_grant`, неверный — `invalid_client`. Значит
  confidential-путь проверен там, где секрет вообще выдают.
- **Atlassian v2**: метаданные объявляют `none`, DCR возвращает
  `token_endpoint_auth_method: none` — но вместе с `client_secret`. Token endpoint
  сначала проверяет grant и только потом клиента, поэтому различить клиентов им
  нельзя.
- **GitLab**: метаданные объявляют только `client_secret_basic|post`, а DCR
  возвращает публичного клиента, `require_pkce: true` и никакого секрета.
  **Сессия поднимается из DCR как публичный клиент с PKCE.**
- **Figma**: `registration_endpoint` объявлен, на `GET` — 404, на `POST` — 403 с
  `vary: X-Figma-Token, Authorization`. Анонимного DCR нет; клиента пришлось бы
  заводить руками, но и это не сработало (см. 3.5).
- **Device flow**: у GitLab `device_code` есть в `grant_types_supported`, но
  `device_authorization_endpoint` не объявлен, `POST /oauth/device_authorization` —
  404, а `/oauth/authorize_device` отвечает `access_denied` клиенту из DCR.
  Библиотека без вендорского знания этот эндпоинт не найдёт — device flow не
  делался.

**Проверено:** в харнессе нет ни одной реализации OAuth для MCP. Стоковый
`dsh-mcp-client` берёт статический `Authorization` из конфигурации; ни PRM, ни
DCR, ни PKCE в дереве пакетов нет.

### 3.2 Atlassian

- `webUrl` не отдаётся клиентам, которых сервер не узнал по имени, поэтому ссылку
  и cloud id даёт `getAccessibleAtlassianResources` — список сайтов аккаунта.
- Markdown приходит с HTML-комментариями редактора (`<!-- … -->`); они убираются на
  входе в читатели (`stripHtmlComments`), кроме ```-блоков.

### 3.3 Sentry

- Топ-левел пятнадцать тулов. `search_issues` принимает запрос **на естественном
  языке** (сервер переводит его сам), отвечает **Markdown-документом** и сам
  предлагает презентацию карточкой; `outputSchema` не объявлена.
- `get_sentry_resource` отдаёт **тот же документ**, что длиннохвостый
  `get_issue_details`, — отдельный тул для деталей не нужен. Длинный хвост
  достаётся через `search_sentry_tools` + `execute_sentry_tool`.
- `update_issue`: `status` (resolve/reopen/ignore) и `assignedTo` в формате
  `user:<id>` / `team:<id|slug>`; справочника людей нет, `whoami` даёт id для
  self-assign.
- Чего в поверхности нет: тула комментариев и breadcrumbs в документе issue.
  Релиз приходит **тегом** (`release: storefront@3.0.1`), а не полем.
- Suspect Commit несёт SHA, автора и **ключ тикета прямо в сообщении коммита**
  (`DEV-5977: …`); Code Location — ссылку на файл в GitLab. Отсюда и взялась
  корреляция.
- `analyze_issue_with_seer` — разбор внешней моделью; в карточку не выводится.
- Побочно: `mcpJson` не читал `structuredContent`, хотя docstring это обещал;
  теперь читает и ставит его первым.

### 3.4 GitLab

- **MCP недоступен, и это факт, а не выбор.** Живой эндпоинт ответил `403 MCP
  server not enabled for any of your groups`: доступ включается на уровне
  top-level группы, а владельца такой группы у пользователя нет. Токен MCP
  принимается только на `/api/v4/mcp`, для REST даёт `401`, а единственный
  объявленный скоуп — `mcp`. Поэтому плагин ходит в REST **личным токеном**,
  запись — `dsh-gitlab/token` (`credentialKey(scope, id)`, а не `credentialKeyFor`:
  тот всегда строит `mcp`/`mcp-<instance>`).
- `/diffs` не отдаёт статистику по файлу: есть только текст патча, `+N/−M`
  считаются из него.
- Состояние треда лежит на **заметках**, а не на треде: `resolvable`/`resolved` у
  заметки, `resolvable` у треда. Тред закрыт, когда закрыты все его разрешимые
  заметки.
- Фильтр «Bots» по имени не работает: реальный CodeRabbit пишет под обычным
  аккаунтом (`code_rabbit_dogedev`), а флаг `bot` GitLab отдаёт в списке MR и не
  отдаёт в дискуссиях. Поэтому в панели фильтр **по сути**: Findings — треды с
  заметкой на строке диффа.
- Листовой эндпоинт MR не отдаёт `head_pipeline` — карточка списка пайплайн не
  показывает (дотягивать по строке значило бы N запросов).
- Лог job режется до последних 64 КиБ.

### 3.5 Figma

- Локальный Dev Mode MCP на `127.0.0.1:3845/mcp`: десять тулов, три промпта, ни
  одного ресурса. `get_metadata` отвечает **XML** (и дописывает абзац-совет агенту
  после закрывающего тега); `get_variable_defs` — плоским объектом `{name: value}`;
  `get_code_connect_map` — объектом по node id и `{}` для ноды без маппинга;
  `get_screenshot` — image-блоком; `get_design_context` — React+Tailwind кодом и
  тем же скриншотом внутри.
- Отдельного тула «выделение» нет: `get_metadata` без `nodeId` отвечает прозой со
  списком страниц, а с выделением — XML выбранной ноды.
- **Удалённый транспорт закрыт:** `registration_endpoint` отвечает `403`
  анонимному `POST`, единственный скоуп `mcp:connect` не значится среди скоупов
  REST-приложения, документация пускает только клиентов из каталога Figma. Режим
  manual client поэтому не делался — это был бы код, который нечем проверить.
- Code Connect **на живом не проверен**: в файле пользователя нет ни одного
  маппинга (60 нод страницы Components, все `{}`), читатель закреплён
  синтетической фикстурой по документированной форме.

### 3.6 Харнесс

- **`ctx.get` в момент активации — гонка.** Сервис виден, только когда фибра его
  провайдера активна, а `webserver` монтируется поздно (его конфиг ждёт
  `webStartup`, тот — `cmdlineArgs` слоя приложения). Симптом первого запуска
  Figma: тулы работают, роут `/dsh-figma/status` отвечает `404`. Лечение —
  `mountIntegrationRoute` через scoped `ctx.inject(["webServer"], …)`.
- **Расписание сессионное.** `ctx.schedule` хранит напоминание за создавшей его
  сессией и доставляет туда же; после простоя приходит только последнее
  пропущенное срабатывание.
- **Индекс, который прочитал Discover, страница держит у себя.** `search`
  принимает `fetchedAt` и до тех пор отвечает по тому же документу, а `install` в
  записи — это точная версия (`name@version`), а не диапазон. Поэтому после релиза
  страница продолжает предлагать старую версию, пока её не перезагрузят: восемь
  попыток поставить `dsh-workflow-plugin@0.1.2` прошли уже после того, как индекс
  начал отдавать 0.1.4 (и Pages успел отдать свой кэш).
- **Реестр — это шов, а не импорт.** Порядок загрузки не важен: scoped
  `ctx.inject` ждёт сервис и снимается вместе с ним, а сборка без плагина-меты
  просто не будит висящую фибру.

### 3.7 agent-browser (B0, 22.10.2026)

Живой прогон на локальной фикстуре: macOS, Chrome 155.0.8059.86,
`agent-browser` 0.35.1. Полная таблица — в [browser.md](browser.md), здесь то,
что меняет решения.

- **Chrome запускается и стрим работает.** `doctor --json` находит Chrome;
  `open file://…` отвечает `browserLaunched: true`; `snapshot -i` на фикстуре —
  **68 байт** на два элемента; скриншот 1280×720 — 81 КБ PNG.
- **Кадры событийные, а не поток.** Свежий зритель получает кадр через **14–15 мс**
  после handshake, но статичная страница за 4 с даёт **один** кадр: screencast
  шлёт изменение, а не видео. Простаивающий рендерер — 0% CPU.
- **Кадр стоит 82 КБ в дефолте и 2.9 КБ в панельном размере.** 1280×720 при
  quality 80 — ~82 КБ JSON (~59 КБ JPEG); `STREAM_QUALITY=20` с
  `STREAM_MAX_WIDTH/HEIGHT` 420×320 — ~2.9 КБ JPEG, разница 28×. `metadata`
  при этом остаётся 1280×720: это размер вьюпорта, по нему считаются клики.
- **Чужой `Origin` стрим-сервер отвергает: 403.** `http://127.0.0.1:58052` — 101,
  `https://evil.example` — 403, без `Origin` — 101. Прямое подключение панели
  сегодня сработало бы, но оно зависит от чужой политики и ломается там, где GUI
  открыт не с loopback.
- **Стрим несёт ленту активности сам.** Типы сообщений: `status`, `frame`, `url`,
  `command`, `result`, `tabs` — то есть «что агент делает» приходит тем же
  сокетом, отдельный слой активности не нужен.
- **Ввод работает.** `input_mouse` из сокета изменил DOM и `document.title` —
  проверено чтением через CLI. Два зрителя одновременно получают все кадры.
- **Шов под это уже объявлен.** Хостовый сервис `ctx.browserUse`: «Reserve the
  sole provider slot… Providers must stop their tools and await owned work before
  releasing this registration» (рядом `ctx.computerUse`). Что читает эту
  регистрацию — открытый вопрос раздела 9; B1 обошёлся без него.
- **B1: цикл проверки UI работает целиком.** `dsh-browser-plugin` запускает
  настоящий Chrome, снимает дерево доступности, кликает по `@eN`, читает
  изменившуюся страницу, консоль и ошибку — живым dry-run'ом на локальном
  HTTP-сервере (11 проверок). Формы ответов CLI, на которых это стоит, —
  таблица в [browser.md](browser.md) §2.1: `refs` оказался объектом, а не списком,
  `click` не возвращает адрес, `doctor` отвечает без конверта.
- **B2: живой вьюпорт работает.** Панель опрашивает `/dsh-browser/panel` раз в
  четверть секунды и рисует кадр отдельным `<img>` с `/dsh-browser/frame`: сокет
  на странице Desktop невозможен, `new WebSocket` на схеме `dsh-app://` падает с
  `SyntaxError`. Хост сам читает скрикаст agent-browser и отдаёт кадр, адрес и
  ленту команд. Стрим живёт только пока кто-то смотрит и только после того, как
  тул доказал, что браузер есть: холодный `stream status` поднимает демон сессии
  (Chrome при этом не запускает — проверено `pgrep`), а `session info` врёт про
  запущенный браузер, потому что отдаёт намерение, а не факт.
- **B3: панель управляет страницей.** Кадр перестал быть крошечным: 1280×720 при
  quality 60 — **31 КБ** против 7.5 КБ у прежних 640×480/quality 30, и текст в нём
  читается. Ввод уходит **тем же сокетом**, что и кадры, — клик (640,508) по
  живому сайту дошёл до `/login`, колесо на 600 сдвинуло `scrollY` на 600, два
  нажатия дали `value: "hi"` в поле. Навигация и `set viewport` — команды CLI:
  у сокета для них сообщений нет. **Координаты пришлось считать не по метаданным
  кадра:** при окне 1280×720 страница внутри — 1280×633 (`innerHeight`), а
  эмулированный вьюпорт 390×844 приходит картинкой 474×800, то есть страница
  вписана в поверхность окна, а остаток — не страница. Размер спрашивается у
  страницы (`eval innerWidth/innerHeight`) один раз на соединение и после смены
  окна; проверено попаданием в кнопку на телефононом лейауте.
- **B3: агент узнаёт, что делал человек.** Первый результат следующего тула
  начинается с фразы «The person at the panel used this browser since your last
  call: …», иначе клик человека двигает страницу, а агент продолжает работать по
  устаревшим рефам и не понимает, почему всё разъехалось. Фраза выдаётся один раз
  (`finalizeContent` + буфер в хабе) и срабатывает даже на упавшем туле.

## 4. Четыре идеи: что сделано

### Идея 1. Dev-проверки ✅

Рецепты живут в `dsh-checks.json` в корне проекта: командой владеет проект, агент
только называет рецепт, а `checks` никогда не принимает произвольную команду.
Парсеры: `tsc`, `biome` (JSON- и pretty-репортер), `eslint`, `vitest`, `jest`,
`pytest`, `generic`. UI: строка тулкола, карточка с итогами и `file:line`, который
открывает файл в панели. Плюс `/checks` и `/checks init`.

**Побочно выяснилось:** biome печатает диагностики в stderr, а счётчики в stdout —
раннер читает оба и берёт счётчик как максимум; `generic` нужен чаще, чем
казалось.

**Осталось:** watch-режим; длинные прогоны через `ctx.jobs`; парсеры `cargo` и
`go test` (проверить их не на чем — ни cargo, ни go не установлены); upstream
`diagnostics` в `dsh-tool-lsp`. Клик по файлу открывает его начало: сиденье
`conversation.chat.turnTail` отдаёт `openFile(path)` без строки.

### Идея 2. Sentry ✅

Провайдер на библиотеке: OAuth-профиль, `/sentry status|login|logout|sync`,
карточка `sentry_present` и панель issue с Resolve / Ignore / Reopen / Assign.
Факты о поверхности — в 3.3.

**Осталось:** Seer в карточку не выводится; если выводить — как предложение
внешней модели, а не как факт.

### Идея 3. GitLab ✅

Транспорт — REST личным токеном (почему — 3.4). `gitlab_present` (MR-список,
замечания ревью, упавшие job), панель MR из четырёх секций, `gitlab_review`
(комментарий, ответ в тред, resolve/reopen, approve) и лог упавшего job.

**Читающие тулы агента.** До них у модели не было способа получить данные из
GitLab для рассуждения — только карточка, — и она уходила в `glab` в шелле искать
токен. Теперь читают `gitlab_list_merge_requests` (скоуп, проект, группа, поиск,
labels, автор/ревьюер), `gitlab_get_merge_request` (поля MR и по запросу дифф,
дискуссии, свежий пайплайн с job), `gitlab_get_job_log` (хвост trace упавшего
job) и `gitlab_read` (любой REST GET — issues, коммиты, ветки, файлы, поиск).
Чтения идут через `GitLabApi` личным токеном из хранилища харнесса: в модель и в
шелл он не попадает.

**Ревью с CodeRabbit** получилось не таким, как планировалось: фильтровать по боту
нельзя (3.4), поэтому «замечания» — это треды с заметкой на строке диффа, и они же
попадают в дайджест.

**Осталось:** ретрай упавшего job из панели (механическое действие);
`DiffBlock` из UI-кита для диффа; связка «упавший job → локальный прогон теми же
рецептами»; режим ревью (агент пишет саммари MR, человек утверждает); список «мои
MR, где мяч на мне»; мультиаккаунт (ключ записи один).

### 5.1 Дайджест ✅

**Сборщик детерминированный, а не «попросим модель».** Дайджест приходит по
расписанию, без человека рядом; если бы он ходил через модель, в неудачный день
пришла бы выдумка вместо фактов.

Состав (каждый пункт — переключатель): задачи Jira в работе и просроченные (вкл),
назначенные, но не начатые (вкл), MR, где ждут ревью (вкл), свои MR, где мяч на мне
(вкл), новые ошибки за сутки (вкл), комментарии CodeRabbit (выкл), вводная фраза от
модели (выкл, **не сделана**).

Что решили по ходу:

- **Заголовок и переключатель блока едут от провайдера** — карточка настроек
  рисуется по установленному, а не по списку в одном месте.
- **Сбой одного блока — строка `unavailable` у этого блока**: «на ревью ничего не
  ждёт» и «GitLab не подключён» — разные факты.
- **Окно — сутки, и это сказано в заголовке блока.**
- **Семь дней — `daily`, меньше — `weekly`:** у сервиса два правила повторения,
  выбор между ними в одной чистой функции.
- **Настройки — один JSON под домашней директорией харнесса**
  (`$DSH_HOME/digest/settings.json`): у дайджеста нет credential-записи, к которой
  их подшить. Файл читается прощающе, запись идёт через rename.
- **Напоминание опознаётся по маркеру в промпте**, а не по заголовку: задача
  пользователя с тем же названием не должна попасть под удаление.
- **Тул `digest` не принимает аргументов:** состав — это настройка.
- **`dsh-integration-host/digest` — отдельный вход библиотеки**, чтобы браузерная
  половина не тянула node-код роута.

## 6. Сквозные решения и риски

- **Мультиаккаунт** — сделано: ключ записи `scope + instance`
  (`dsh-gitlab/mcp`, `dsh-gitlab/mcp-work`); старые записи читаются как `default`,
  `instancesOf` перечисляет то, что лежит в сторе. Плагины пока держат по одному
  аккаунту: UI для нескольких — вместе со вторым провайдером.
- **Локальный маршрут без аутентификации.** `/dsh-*` доступен любому локальному
  процессу, а с записью в Jira это уже не только чтение. **Уточнено в B2:**
  admission у харнесса есть — `connection.admitConnection(request)` — но это
  admission для *своих* аутентифицированных peers: он отбивает с 403 даже
  loopback-запрос с `Origin` GUI, а обычные `register`-маршруты не спрашивают его
  вовсе (`GET /dsh-figma/status` снаружи отвечает `200` без токена). Поэтому
  панель браузера ходит обычным относительным запросом, а честный вариант на
  будущее — тот же admission на обычных маршрутах, и это правка харнесса, а не
  каждого плагина. **Не решено.**
- **Кэш и лимиты.** Списки кэшировать на десятки секунд, уважать `Retry-After`, не
  долбить API в цикле.
- **Права на запись — социальные действия только с подтверждением.** Три уровня,
  которые не смешиваются: механическое действие (переход статуса, назначение,
  resolve) идёт обычным тулом и гейтится permission-пайплайном; социальное
  (комментарий, ответ в тред, резолв треда, approve) требует явного `confirm` и без
  него возвращает структуру «что будет отправлено»; по расписанию не пишется
  ничего вообще.
- **Версионирование** — монорепа + changesets, `engines.dsh` у каждого бандла;
  библиотеки — обычные semver-зависимости и тоже публикуются, потому что
  `devDependencies` опубликованного плагина называют их версиями.
- **`workspace:` в публикуемых манифестах запрещён.** `changeset publish` зовёт
  `npm publish`, а npm протокол `workspace:` не переписывает (в отличие от
  `bun pm pack`), поэтому внутренние зависимости записаны диапазонами, а
  `bun run market --check` не даёт протоколу вернуться.
- **Тесты.** У библиотек — чистые решения и бридж против локального MCP-сервера (у
  `mcp-oauth` ещё живой conformance на пять эндпоинтов); у плагинов — парсеры на
  записанных потоках, роуты и тулы против поддельного канала, живой dry-run. Плюс
  аудит бандлов после сборки.
- **Приватность.** Токены не попадают ни в логи, ни в контекст модели; в карточки
  идёт только то, что нужно человеку.

## 8. Решения (приняты)

1. **Монорепа.** Общие библиотеки — workspace-зависимости, релизы — changesets.
2. **Без скоупа, имена `dsh-...-plugin`** у бандлов; библиотеки без суффикса.
3. **Только gitlab.com.** Manual-client режим для GitLab не нужен: DCR выдаёт
   публичного клиента. **Уточнено на M5:** вход в GitLab — личный токен и REST.
4. **Figma Dev Mode есть**, приложение просто не запущено; локальный транспорт — в
   объёме M6, и перед кодом обязателен спайк.
5. **Дайджест делаем, с настройкой** — время и состав; дизайн в 5.1.
6. **Социальные действия — только с подтверждением** (механика в разделе 6).
7. **Пока библиотекой.** Апстрим в DSH — отдельным решением позже; public
   conformance-набор из M1 и есть аргумент для него.
8. **Общий код, свой тип вкладки на провайдера** (M4). Один kind с реестром
   провайдеров требовал бы общего рантайма у бандлов, которого у них нет.
9. **Хостовый каркас — тоже библиотека** (M4): `dsh-integration-host` владеет тем,
   что одинаково у всех.
10. **Figma — только локальный транспорт** (M6): удалённый закрыт для сторонних
    клиентов (3.5). Шов оставлен — профиль без блока `oauth`.
11. **Дайджест собирается через реестр источников** (M7): контракт источника в
    `dsh-integration-host`, реестр предоставляет плагин дайджеста, интеграции
    регистрируют блоки через scoped `ctx.inject`.
12. **Расписание дайджеста привязано к сессии** (M7): *что* и *когда* задаёт
    секция настроек, *где* — `/digest on` в нужной сессии; смена времени
    пересоздаёт напоминания всех сессий.
13. **Полировка интерфейса** (21.10.2026): одна страница Integrations вместо пяти
    секций навигации (у дочернего слота может быть ровно один объявитель); Digest
    остаётся своей секцией; карточка настроек показывает одно состояние за раз;
    метаданные в панелях — строки, а не бейджи, ответственный — меню.
14. **Полировка, второй заход** (21.10.2026): один отчёт `checks` на ход —
    последний (у определения карточки опция `keep: "all" | "last"`); строка
    тулкола говорит человеческим ярлыком, имя тула остаётся в подсказке; загрузка
    панели — примитивами харнесса по центру; HTML-комментарии провайдера не
    доезжают до читателя.
15. **Корреляция — второй реестр, а не импорт** (M8). Контракт факта и ссылки
    (`error | commit | change | task`) объявлен в `dsh-integration-host`, реестр
    `ctx.correlationSources` предоставляет `dsh-correlation-plugin`, интеграции
    регистрируют адаптеры. Провайдер отвечает про ту ссылку, о которой его
    спросили, фактом, а факт несёт ссылки дальше: обход не знает, как выглядит
    цепочка. Договор между провайдерами — тоже ссылка (Sentry кладёт адрес файла,
    GitLab сам читает из него проект), поэтому ни один не знает имени другого.
    Обход — в глубину, чтобы карточка читалась цепочкой, а не слоями.
16. **Market-индекс генерируется и валидируется валидатором харнесса** (M8):
    источник — пакеты плюс `scripts/market/catalog.mjs`, результат —
    `docs/market.json`, `bun run market --check` ловит расхождение (кроме времени
    публикации: оно меняется в момент релиза). Иконки инлайнятся, `publishTimestamp` берётся из реестра (до первого релиза — из
    коммита). Пакеты публикуемы, релиз — changesets, `dsh-workflow-plugin`
    подключает все бандлы одной строкой профиля.
17. **Сборка — библиотека** (M8, закрывает долг §5.3 AGENTS.md):
    `dsh-plugin-build` владеет обеими половинами, инлайном CSS, картой
    workspace-библиотек и единственным ключом `__DSH_STYLES__`; `build.mjs`
    плагина — две строки.
18. **Движок агентского браузера — `agent-browser`, своего CDP не пишем** (B0).
    Он уже даёт снимок дерева доступности с `@eN`-рефами, именованные сессии,
    WS-стрим вьюпорта с приёмом ввода и политику доменов и подтверждений;
    Playwright как библиотека на машине не установлен, а свой screencast — это
    переписывание готового против браузера, который обновляется сам.
19. **Живой вьюпорт идёт через WS-upgrade на origin харнесса, а не прямым
    подключением панели к порту стрима** (B0). Стрим-сервер пускает только
    loopback-`Origin` (чужой — 403), а GUI харнесса бывает открыт и не с
    loopback; прокси даёт один origin, скрытый порт, переподключение после
    перезапуска демона и одно место для режима «только смотрю». Шов —
    `webServer.registerUpgrade`, тот же, на котором в харнессе живёт WS
    `api-gateway`.
20. **Headless по умолчанию; профиль реального Chrome — opt-in на сессию** (B0).
    Окно не крадёт фокус, а залогиненное состояние не попадает агенту без
    явного согласия человека.
21. **Словарь из шести тулов плюс лазейка `browser_run`, а не обёртка над всеми
    командами CLI** (B0). Контекст агента дороже нашего удобства, лазейка
    закрывает длинный хвост — вкладки, сеть, cookies, a11y-аудит. Лента
    активности в панели берётся из сообщений `command`/`result` самого стрима,
    а не из своего слоя.22. **Процесс браузера идёт через `ctx.subprocess`, а не через `ctx.shell`** (B1).
    Bash-шов применяет файловую песочницу харнесса, а Chrome под песочницей не
    стартует (измерено в B0: `Failed to initialize sandbox`), и он принимает
    командную строку, тогда как список аргументов исключает переинтерпретацию
    URL и селектора, пришедших от модели.
23. **Свой браузер на разговор — именем сессии, а не своей сокет-директорией**
    (B1). `--session dsh-<id>` при сокет-директории CLI по умолчанию: `bash`-вызов
    с тем же именем попадает в тот же браузер, общий `default` не трогается, а
    дашборд самого CLI видит наши сессии. Отдельный неймспейс остаётся
    настройкой на потом.
24. **Живой вьюпорт — опрос и одна картинка, а не сокет** (B2, пересмотрено после
    измерения). Сокет не годится дважды: прямое подключение к стриму
    agent-browser отбивается по `Origin` (403), а свой WS на origin харнесса
    невозможен, потому что страница в Desktop живёт на `dsh-app://` и
    `new WebSocket(…)` падает с `SyntaxError`. Поэтому панель опрашивает
    `GET /dsh-browser/panel` раз в четверть секунды и рисует кадр отдельным `<img>` с
    `GET /dsh-browser/frame` — тот же относительный запрос, которым ходят все
    остальные панели репозитория. Счётчик кадра в адресе — ключ кэша: без него
    неизменившийся адрес не перезапросили бы и новый кадр остался бы невидимым.
    Хост при этом читает скрикаст agent-browser сам: один WS-клиент на сессию со
    своим кодеком (~130 строк на четыре опкода вместо зависимости `ws`).
25. **Хаб живёт только пока смотрят и только после доказательства** (B2).
    Соединение со скрикастом открывается по первому опросу и закрывается через
    десять секунд после последнего; `stream status` спрашивается только после
    успешного тула, потому что на холодной сессии он поднимает демон, а
    `session info` не используется вовсе — `browserLaunched` там намерение, а не
    факт (измерено: `true` при нуле процессов Chrome).
26. **Ввод человека — сообщение в том же сокете, что и кадры** (B3). Клик, колесо и
    клавиши уходят `input_mouse`/`input_keyboard` в уже открытое соединение со
    скрикастом: отдельный процесс CLI на каждый клик — это 200 мс и мигающий
    браузер. Своими командами остаются только те два действия, у которых в
    протоколе нет сообщения: навигация и `set viewport`.
27. **Лента — общая: агент и человек в одной истории** (B3). Действия человека
    попадают в ту же ленту строками `human` («You clicked 412×188»), а не в
    отдельный список: вопрос, на который отвечает лента, — «что случилось со
    страницей», и кто это сделал, уточнение, а не второй экран.
28. **Размер страницы спрашивается у страницы, а не берётся из метаданных кадра**
    (B3). Ни `deviceWidth/Height` кадра, ни `status` стрима не отвечают на вопрос,
    в каких пикселях меряется клик: при окне 1280×720 страница внутри 1280×633, а
    эмулированный вьюпорт 390×844 приходит картинкой 474×800 — страница вписана в
    поверхность окна, и остаток поверхностью не является. Поэтому хост один раз на
    соединение (и ещё раз после смены метаданных кадра) спрашивает
    `eval "JSON.stringify([innerWidth, innerHeight])"`, а панель делит точку в
    пикселях картинки на масштаб вписывания. Цена — один вызов CLI на открытие
    панели; альтернатива — стабильный промах до 14% по вертикали.
29. **Вмешательство человека доходит до агента результатом тула, а не сообщением**
    (B3). Действия из панели копятся в хабе и вклеиваются первым блоком в
    ближайший результат браузерного тула через `finalizeContent`. Отдельное
    сообщение в разговор выглядело бы как реплика пользователя и стоило бы
    токенов на каждый ход; а поле в схеме ответа пришлось бы добавлять пяти
    тулам. Цена — фраза приходит только когда агент снова трогает браузер, а это
    ровно тот момент, когда она нужна.
30. **Конфиг — схема, а не ручной разбор, и поля — `volatile`** (B4). `Config`
    через `@deepseek-ai/schemastery`: дефолты, границы и описания полей живут в
    одном месте, Loader валидирует патч до активации, а страница настроек берёт
    из схемы список полей и подсказки. `volatile` — не украшение: без него
    `settings.write` отказывает («Plugin entry has no volatile fields»), а с ним
    значение читается в момент использования, и сохранение не перезапускает
    плагин. Обратная сторона — значение вне границ теперь отказ активации, а не
    молчаливый дефолт; форма, показывающая значение, которого браузер не
    получил, врёт убедительнее ошибки.
31. **Страница настроек — форма харнесса, а не своя** (B4). `SettingsFormModel`
    из UI-кита копит правки и пишет одной ревизионной записью по Save; плагин
    объявляет только схему, подписи и `Config`-элементы. Свой JSX-редактор дал бы
    вторую реализацию сохранения, конфликтов ревизий и «сбросить к дефолту».

## 9. Что ещё не решено

- **Аутентификация локального маршрута** — см. раздел 6. С M7 к списку таких
  роутов добавился `/dsh-digest`, а с M9 — четыре маршрута панели браузера
  (`/dsh-browser/panel`, `/frame`, `/close`, `/input`), которые открыты так же;
  `/input` вдобавок пишет в браузер, то есть это уже не только чтение.
- **Вводная фраза от модели в дайджесте.** Сборщик детерминирован, а хост-половине
  вне турна неоткуда взять модель, не заведя отдельный маршрут к ней.
- **Живой прогон дайджеста и корреляции.** Источники и адаптеры покрыты офлайн, на
  записанных формах ответов; на живых аккаунтах ни дайджест, ни `correlate` не
  запускались.
- **Локализация.** Через locale-сервис идут только `meta.title` и
  `meta.description` пакетов; строки клиентских половин английские. Объём — около
  230 строк в семи плагинах плюс общие строки `dsh-integration-ui`; для `ru` нужен
  отдельный бандл-языковой пакет, потому что язык регистрируется один раз, а
  клиентские половины плагинов — отдельные бандлы.
- **Upstream-вклад.** Решение 7 в силе; conformance-набор из M1 — аргумент для PR в
  `dsh-mcp-client` (`authProvider`) и `dsh-tool-lsp` (`diagnostics`).
- **Парсеры `cargo` и `go test`.** Писать их не на чем: ни cargo, ни go не
  установлены, а сочинять формат по памяти репозиторий не берётся.
- **Удалённый транспорт Figma** — вернуться, если Figma откроет динамическую
  регистрацию или добавит `mcp:connect` в скоупы OAuth-приложения.
- **Аутентификация локального WS `/dsh-browser/stream`** (M9). Тот же долг, что и
  у `/dsh-*` роутов, но с записью: это клики в браузере с куками сессии агента.
  Решить до B2, а не после.
- **Что читает `ctx.browserUse`** (M9). Харнесс объявляет хостовый шов
  «sole provider slot» с требованием остановить тулы перед освобождением
  регистрации; **проверено к B2: потребителя в собранном дереве нет** (слово
  встречается один раз, в реестре контрактов). Плагин владеет тулами и панелью
  сам; вернуться, если у шва появится потребитель.
- **Смена размера кадра на ходу** (M9). В спайке `screencast_start` не подействовал:
  размер задаётся env при запуске демона. Вернуться, если понадобится менять
  качество без перезапуска.
- **Headed-режим, профиль реального Chrome и живые сайты** (M9). И спайк, и
  живой dry-run B1 гоняли на локальной странице; поведение на настоящем сайте с
  авторизацией не измерено, как и включённое окно.
- **Что остаётся от демона agent-browser после выгрузки плагина** (M9). CLI
  отцепляет свой демон от запустившего его процесса, а субпроцесс-шов владеет
  только запущенной командой. Проверить, переживает ли демон выгрузку плагина и
  не убивает ли teardown чужую сессию, — до B4.
